# Comprehensive functional, quality, and performance testing

Version 0.14.0 adds one entry point for the recurring optimize/test/retest loop:

```bat
test\test_everything.bat mvs-dumps-root
```

## Default cycle

The default cycle:

1. selects `mvs_2019-03-19` when present (otherwise the first discovered real
   snapshot);
2. runs `test_all.bat` over the complete public regression matrix;
3. analyzes public-test `elapsed_ms` by tool/scope and writes outlier tables;
4. runs `test_fast_archive_sweep.bat` on the three-snapshot synthetic archive;
5. validates a complete full-archive fast plan without performing the long real
   execution.

The public regression still has 1,056 assertions: 1,053 expected passes and
three data-dependent note exact-match skips on the established 2019-03-19
baseline.

## Full fresh archive cycle

To execute the real archive as part of the comprehensive cycle:

```bat
test\test_everything.bat ..\mvs_dumps_archive --full-archive --workers 8
```

The full mode explicitly uses `--no-cache`. This is intentional: a performance
regression must not be hidden by a cached result from an earlier fast worker.

After execution it runs `check_archive_sweep_quality.bat` against the new
results folder. The interactive HTML report is generated by the sweep.

## Strict performance gate

By default performance outliers are warnings so that a new future dump can be
inspected rather than automatically breaking the functional acceptance result.

Promote outliers to failures with:

```bat
test\test_everything.bat ..\mvs_dumps_archive --strict-performance
```

or:

```bat
test\check_archive_sweep_quality.bat results-folder --strict-performance
```

Thresholds are intended as regression/outlier detectors, not hardware
benchmarks.

## Existing archive results

Analyze a previously completed run during the comprehensive cycle:

```bat
test\test_everything.bat ..\mvs_dumps_archive --archive-results C:\path\archive-sweep-results-...
```

## Public-tool performance output

`test\analyze_test_performance.bat test-results-folder` reads the timed
`all-results.tsv` produced by the generated public regression harness and
writes:

```text
performance-analysis\
    all-timed-cases.tsv
    performance-by-scope.tsv
    performance-by-tool.tsv
    performance-outliers.tsv
    summary.txt
```

The tool table aggregates calls, total time, median, p95, and maximum elapsed
time so the largest public-tool costs can be optimized and the identical test
matrix rerun afterward.

## Archive quality/performance output

`test\check_archive_sweep_quality.bat results-folder` verifies:

- plan and run row counts;
- unique and complete plan indices;
- run/plan metadata identity;
- zero logical `FAIL` rows;
- summary counters against authoritative `runs.tsv`;
- every `SOURCE_MISSING` classification against frozen `snapshots.tsv`
  availability;
- required fast evolution outputs and summary row counts;
- note observation-count bounds and retained raw HTML;
- per-dump retention accounting;
- quality flags;
- per-logical-tool elapsed-time outliers;
- full snapshot-batch elapsed-time outliers.

It writes:

```text
quality-check\
    summary.txt
    performance-by-tool.tsv
    performance-outliers.tsv
    performance-by-batch.tsv
    performance-batch-outliers.tsv
    unexpected-source-missing.tsv   (only when needed)
```

## Fast synthetic acceptance

`test\test_fast_archive_sweep.bat` has no prerequisite. Its three-snapshot
fixture deliberately includes:

- an ordinary layout;
- a nested `mvs_dmp` layout;
- case/whitespace/ID normalization changes;
- legacy `<h3>Title [ID: ...]</h3>` notes;
- newer `<h1>Title</h1>` notes;
- one unchanged note across all three snapshots;
- a one-snapshot note;
- changed product/variant membership.

The test asserts 1,306 logical checks, exact fixed history/all-ever trees,
4 all-ever product states, 4 all-ever variant states, 5 note versions,
5 note bodies, five raw-note variants, and a three-snapshot observation count
for the unchanged Keep note.

## Optimization loop

A normal performance-development cycle is:

```text
test
  -> inspect performance-by-tool / performance-by-batch
  -> optimize maintained source
  -> regenerate standalone artifacts
  -> rerun identical functional tests
  -> rerun fresh performance test
  -> require no functional regression and review performance delta
```

Cached archive runs are useful for frequent catalog validation. Fresh
`--no-cache` runs are the authoritative performance measurement.

## Acceptance definition and recurring optimization loop

The user requires a complete start-to-finish real-archive run before the fast
archive path is considered fully validated. Resume support remains essential
for fault recovery, but an interrupted/resumed run is not the final acceptance
artifact.

The intended recurring loop is:

```text
functional regression
    -> fast synthetic acceptance
    -> fresh real-archive run
    -> quality/integrity check
    -> performance outlier review
    -> optimization
    -> rerun the same gates
```

A performance change is accepted only when the same functional assertions and
return-code/output contracts remain clean afterward.

`--full-archive` testing should use a no-cache/fresh execution path for the
performance baseline. Ordinary frequent runs may use the content cache.

The project goal is to make complete archive testing practical enough to run
regularly during the week.
